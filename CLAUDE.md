# CLAUDE.md: Spicetify Fixes

A personal Spicetify CLI extension that applies known fixes for Spicetify bugs until Spicetify releases them. Not a Marketplace extension: no `manifest.json`, no `preview.png`, no `spicetify-extensions` topic. No support for others.

## Files

| File | Purpose |
|---|---|
| `spicetifyFixes.js` | The extension. Plain JS, one async IIFE, `"use strict"`, no dependencies. |
| `scripts/manage.ps1` | Install, update, uninstall and link logic. Windows PowerShell 5.1, **ASCII-only**. |
| `install.cmd`, `update.cmd`, `uninstall.cmd` | Double-clickable wrappers around `manage.ps1`. |
| `README.md` | User docs, one section per fix. |

## Adding a fix

1. Add an entry to `FIXES` with every field: `id`, `title`, `symptom`, `upstream` (array of URLs), `spicetifyVersions`, `waitFor()`, `detect()`, `apply()`.
2. `spicetifyVersions` lists only Spicetify versions you verified the fix on. Note the Spotify version and date in a comment.
3. `detect()` returns true only while the bug is present right now, and false once it's gone (upstream fix, Spotify update, or after `apply()`). The runner relies on that to report `not-needed` and `failed`.
4. Never throw out of the IIFE. The runner isolates each fix in try/catch; helpers outside it (observers, listeners) catch their own errors.
5. Use `window.Spicetify?.x`, never bare `Spicetify?.x`.
6. Add the README section (see below).

If something depends on the live Spotify DOM or Spotify's modules and can't be known from this repo, give the maintainer a devtools console snippet to verify it instead of guessing. Facts already verified (in the fix comments and README) are not re-derived.

## Extending a fix to a new Spicetify version

`untested-version` in `__fixes.status()` means the bug is still present on a Spicetify version not in the list. Verify the fix by hand on that version, then add the version to `spicetifyVersions`. Never add a version you haven't verified.

## README section per fix

Under *What it fixes*, one section titled <title> (`<id>`) with: **What you notice**, **Cause** (one or two plain sentences), **Affected** (versions), **Upstream** (links labelled e.g. "closed, not merged", "fixed on main, not released"), **Stops applying**. Add a matching row to the troubleshooting table if the fix has its own failure mode.

The README is written for an ADHD brain: one action per numbered step, the exact command to copy, and "You should see: ..." after each step.

## Development (Windows)

```powershell
spicetify enable-devtools        # Ctrl+Shift+I in Spotify, then __fixes.status()
spicetify watch -e               # reload extensions on save
```

After a Spotify update, run `spicetify backup apply`, then check `__fixes.status()`: a fix whose bug is gone shows `not-needed`.

## Conventions

- British English everywhere.
- No "Generated by/with Claude Code" footers in commits, issues, PRs or anywhere else.
- Commit and push to `main`, one logical change per commit.
- Bump the version in the header comment and in `window.__fixes` together.
